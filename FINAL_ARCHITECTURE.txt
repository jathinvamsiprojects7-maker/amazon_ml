2. Final Pipeline
Stage 0 — Validation foundation

Load:

train_source1.tsv
train_source2.tsv
train_source3.tsv
train_ground_truth.tsv

Then later:

test_source1.tsv
test_source2.tsv
test_source3.tsv

Validate:

schema
IDs
duplicates
malformed rows
row counts
missingness
encoding

Also implement the submission validator early.

Stage 1 — Normalization

Never destroy the original values.

Maintain:

raw_name
raw_address
raw_country

and create:

name_norm
address_norm
name_tokens
address_tokens
address_digits
address_key

Initial normalization:

Unicode normalization
case normalization
whitespace normalization
punctuation cleanup
safe character handling

Do not automatically force aggressive typo correction, transliteration, abbreviation expansion, etc. Those remain experiments.

3. Caching & Data Representation

Use:

int32 internal IDs
        ↓
Parquet cached representations
        ↓
Reusable indexes

Cache:

normalized names
normalized addresses
tokens
digit keys
compact IDs
retrieval indexes
candidate pairs
negative pairs
expensive features

Use configuration/input versioning so stale caches aren't accidentally reused.

4. Candidate Generation

This is one of the most important components.

For every S1:

C_name
C_address
C_digit
C_rare_token
C_ngram

C = UNION(all channels)
Channel 1 — Exact normalized name
name_norm → S2/S3 IDs

High precision, useful for formatting variation.

Channel 2 — Exact normalized address
address_norm → S2/S3 IDs

Useful when the business name is ambiguous.

Channel 3 — Address digit/key

Use:

street numbers
postal codes
digit sequences
other stable address keys
Channel 4 — Rare informative tokens

Don't treat generic words such as:

store
center
the

the same as informative tokens.

Use token frequency to determine informativeness.

Channel 5 — Sparse character n-grams

Use sparse character representations to retrieve fuzzy candidates such as:

apollo medical center
apollo medical centre
apolo medical center

Never construct a dense S1 × S2/S3 similarity matrix.

The architecture explicitly requires bounded sparse retrieval.

Optional

Only experimentally:

phonetic retrieval
additional token retrieval
multilingual/semantic retrieval
5. Candidate Union

Every retrieval result keeps provenance:

S1_ID
candidate_ID
source
exact_name
exact_address
digit_key
rare_token
ngram
...

Example:

S1_100
S2_500

exact_name = 1
digit_key   = 1
ngram       = 1

The number and combination of retrieval channels become ML features.

6. Generic-Name Protection

For names appearing extremely frequently:

ABC
medical center
physical therapy
...

don't blindly expand the entire bucket.

But also don't delete the bucket just because it is large.

Measure:

bucket size
true-match recall
candidate volume
secondary evidence

Then experimentally determine safe handling.

The uploaded architecture specifically keeps this as an experimental retrieval decision rather than hard-coding a threshold.

7. Candidate Recall Gate

This is a validation/experiment gate, not something that requires test ground truth.

9. Training-Pair Construction
Positives

Ground-truth matches.

Negatives

Use four categories:

1. Random negatives

2. Same-name / different-address

3. Same-address / different-name

4. Near-miss / high-similarity negatives

Hard-negative candidates must:

NOT be known GT positives
NOT use validation labels
NOT use test information

and mining stays inside the training partition.

The negative ratio is experimental, not fixed beforehand.

10. ML Model
L0 — Deterministic baseline

Purpose:

sanity check
pipeline validation
establish baseline

Not necessarily final.

L1 — Logistic Regression

First real ML model.

Advantages:

fast
interpretable
useful baseline
L2 — LightGBM / GBDT

Nonlinear model capable of learning interactions between:

name
address
digits
rarity
missingness
contradictions
provenance

Do not assume LightGBM wins.

Compare it against Logistic Regression on the same validation setup.

11. Validation

Split by S1 entity, not individual pairs.

Correct:

S1_A
 ├── positive
 ├── negative
 ├── negative
 └── negative

→ all TRAIN

Another S1:

S1_B
 ├── positive
 ├── negative
 └── negative

→ all VALIDATION

Never split pairs from the same S1 across train/validation.

Also evaluate separately:

zero-match
singleton
multi-match

S1 → S2
S1 → S3

missing-address
generic-name
hard negatives
retrieval failures
false positives
false negatives

The architecture explicitly requires S1-grouped validation and cardinality-specific analysis.

12. Iterative Hard-Negative Mining

After the initial model:

Model
 ↓
Run over training candidate universe
 ↓
Find known negatives with very high predicted scores
 ↓
Add to hard-negative pool
 ↓
Retrain
 ↓
Evaluate on untouched validation

Repeat only if validation Macro F₀.₅ improves.

This is one of the key advanced ML components in our pipeline.

13. Threshold Optimization

The model outputs:

P(match | S1, candidate)

Then search for the threshold that maximizes:

S1-level Macro F₀.₅

First:

global threshold

Then experimentally:

threshold_S2
threshold_S3

Keep separate thresholds only if they produce reproducible held-out improvement.

14. Final Matching Logic

Absolutely no final top-1/top-5/top-10 restriction.

For each S1:

candidate → ML score

Then:

score >= threshold → MATCH
score < threshold  → REJECT

Therefore:

0 candidates pass → []

1 candidate passes → [A]

7 candidates pass → [A,B,C,D,E,F,G]

This preserves the actual 0/1/many structure of the challenge.

15. Final Outputs

Generate:

candidate_pairs.tsv

containing the final candidate universe.

And:

matching_results.tsv

containing accepted matches.

Guarantee:

matching_results ⊆ candidate_pairs

Then run the official/local validator.

The final submission package follows the required structure.
